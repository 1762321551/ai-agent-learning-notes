## 实际输入、模型与运行条件

沿用原项目故意有缺陷的重试模块和三个合成轨迹。两条 `PAYMENT_DECLINED / retryable=false` 轨迹原本分别调用 4 次、3 次，诊断模块据此形成有两个支持案例的故障簇。第三条是可恢复超时。没有真实付款、库存服务或生产流量。

真实模型请求为 `deepseek-official / deepseek-flash`，temperature=0，thinking disabled，max_tokens=1800，JSON 输出。只调用 1 次：HTTP 200，finish_reason=stop，输入 887 tokens、输出 321 tokens、共 1208 tokens；服务商未报告货币费用，本报告不估算价格。响应 ID 为 `c116bba5-572e-46f1-a2c1-1969045c74aa`。

模型看到诊断、稳定源码和负对照的拒绝原因。它返回完整候选源码与预期影响，添加永久错误判断，并保留临时错误重试上限和旧熔断阈值。候选保存在独立目录，没有写回稳定模块。

## 原验证门怎样处理缺失环境

原项目要求候选在无网络、只读、资源受限的 Docker 容器中运行。本机未发现 Docker 命令。实际调用原 `validate_candidate`，其 `sandbox_execution=false`，随后行为/灰度/回滚门均未通过；原路径关闭失败并拒绝候选。结果保存在 `original-docker-gate.json`。

我们没有把 AST 静态检查标成容器隔离。适配执行器把一小部分 Python 语法当作纯策略语言，逐节点计算条件、比较和返回值，**没有 exec/eval 候选源码**。原 `sandbox_runner.py` 中的行为断言原样保留，运行时仅把其源码执行入口换成这个受限解释器。适配证据把执行项命名为 `bounded_interpreter_execution`。

因此本次证明的是狭窄策略语言中的提案—验证闭环；没有证明任意模型生成 Python 能在宿主机安全运行，也没有完成原容器网络、权限与资源限制验收。

## 影子执行、回滚与保护面

合成影子流量实际驱动策略：

- 连续四个永久拒绝事件，真实候选只执行第一次，然后熔断；
- 两个临时超时后接成功，真实候选执行三次并完成；负对照第一次就停止，无法恢复；
- 稳定版本写成独立回滚工件，字节哈希与原稳定文件相同；重新加载版本 1.0.0 后，临时错误路径仍执行到成功。

这是内存策略/合成夹具层面的灰度与回滚，没有部署或恢复生产服务。`release_to_canary` 这一原项目决定值的 scope 已明确收窄为 synthetic shadow fixtures only。

验证前后对稳定模块、轨迹、原行为验证代码和适配执行器计算 SHA-256，结果一致；固定源码副本与原检出项目的受保护文件逐字节一致。生成前保存的稳定文本也与验证时稳定文本相同。哈希证明的是这些记录范围内的保护面，没有扩大宣称完整操作系统权限隔离。

另构造八类执行器负例：导入、通过 builtins 写文件、无限循环、网络调用、函数调用、属性访问、函数签名改变和空策略，全部在解释前拒绝。这是受限解释器的行为测试，不是通用安全审计或完整攻击面证明。

## 原要求差距与学习结论

本次沿用故障簇、真实候选、负对照、原行为断言、同门拒绝/接收、影子流量与回滚工件；实际模型换为现有 DeepSeek，执行器缩小为纯策略 AST。Docker 不可用是原版本未完整复现的关键差距。

尚未完成：原容器镜像和权限/资源门、多任务多 seed 统计、真实业务灰度、生产回滚与长期能力保持。一次候选成功不能证明模型能持续自主进化。

对我最直接的启发是：把“不要重复调用”变成程序规则以后，仍要同时测试可恢复故障。真实模型能生成看起来正确的补丁，最终是否接收要由它无法修改的证据和验证逻辑决定。反例与原失败门应一起保存，学习记录才不会只呈现成功路径。
